AWS Event-Driven Architecture – Event Processing, Ordering and Atomic Publishing

While researching Event-Driven Architecture on AWS, I identified a critical paradox: A system can process all events with 100% success yet still generate incorrect business data due to Race Conditions. This stems directly from the asynchronous nature of decoupled services, particularly when orchestrating Amazon S3, EventBridge, SQS, AWS Lambda, and DynamoDB.

1. WHAT IS THE PROBLEM HERE?

Amazon S3 Event Notifications operate on an At-Least-Once Delivery model, providing no inherent guarantee that events arrive exactly once or in chronological order.

Suppose an AI document processing pipeline updates a file from Version A to Version B:

  • Lambda A: Processes baseline Version A in 15 seconds.
  • Lambda B: Processes updated Version B in only 4 seconds.
  • Outcome: B completes first, but Lambda A finishes later and overwrites the newer result with stale data.

Both Lambda invocations succeed with HTTP 200, yet the final persisted business outcome is completely corrupted.

Core reality: Every individual AWS service worked as designed, yet the business result became corrupted due to uneven invocation latency across distributed workers.

2. WHY ARE IDEMPOTENCY AND SQS NOT ENOUGH?

Engineers commonly assume that applying Idempotency and SQS FIFO queues will eliminate race conditions in event-driven systems. In practice, both exhibit fundamental boundaries:

  • Idempotency: Prevents duplicate side-effects from identical event retries, but cannot prevent an older stale event from overwriting a newer result.
  • Amazon SQS FIFO: Enforces strict ordering within Message Groups, but cannot restore chronological order if events were already delivered out-of-order prior to entering the queue.
  • TOCTOU (Time-of-Check to Time-of-Use): Even when a Lambda inspects object versions before processing, underlying data can change during execution.

3. PROPOSED ARCHITECTURAL SOLUTION

Rather than allowing Lambda functions to directly overwrite shared storage, the recommended pattern blends five core mechanisms:

  • S3 Versioning: Retrieve the exact input data version. Guarantees workers read the specific object version tied to the event.
  • S3 Sequencer: Determine event sequence order on the same object key using the physical hexadecimal timestamp in S3 event payloads.
  • Immutable Output: Each Lambda writes results to a dedicated immutable path (e.g., output/{key}/{version_id}/result.json), preventing direct overwrite conflicts.
  • DynamoDB Conditional Write: Control result publishing using atomic Compare-and-Swap conditional updates. Only updates state if the sequencer is newer.
  • Reconciliation: Recover interrupted tasks and reconcile state inconsistencies when partial failures occur.

DynamoDB Atomic Conditional Update Pattern (Compare-and-Swap):

UpdateItem(
  Key = { "object_key": "document-123.pdf" },
  UpdateExpression = "SET latest_version = :v, result_uri = :uri, s3_sequencer = :seq, updated_at = :ts",
  ConditionExpression = "attribute_not_exists(object_key) OR s3_sequencer < :seq",
  ExpressionAttributeValues = {
    ":seq": event.s3.object.sequencer,
    ":v": event.s3.object.versionId,
    ":uri": "s3://bucket/output/doc-123/v2/result.json",
    ":ts": "2026-11-04T10:30:00Z"
  }
)

Under this architecture, Lambda A can finish after B without ever overwriting B's published result.

However, Amazon S3 and DynamoDB do not share an atomic two-phase commit transaction. Systems must incorporate Retry and Recovery mechanisms to handle partial failures when S3 writes succeed but DynamoDB updates are interrupted.

4. CONCLUSION & PRINCIPLES

In cloud architecture: 100% successful Lambda invocations do not equate to 100% correct business state.

Instead of attempting to force every distributed event to process in strict serial order, architectures should control which version is permitted to publish the authoritative result.

“100% Lambda Invocations successful does not equal 100% business correctness.”

Core Distributed Design Principles:

  • 1. Decouple Processing from Publishing: Leverage Immutable Output for processing and atomic pointers for publishing.
  • 2. Enforce Ordering at the Destination: Use S3 Sequencers and DynamoDB ConditionExpression instead of fragile queue arrival order.
  • 3. Design for Partial Failure: Build Reconciliation Workers to automatically heal cross-service inconsistencies.
