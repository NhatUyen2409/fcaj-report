5.2 – Điều kiện chuẩn bị

Trước khi triển khai nền tảng Nutrition E-Commerce trên AWS, người học cần chuẩn bị tài khoản AWS, các công cụ phát triển, quyền truy cập IAM và nơi lưu trữ Terraform State.

Bài thực hành hướng dẫn kiểm tra môi trường, cấu hình AWS IAM Identity Center và khởi tạo Terraform Backend trên Amazon S3.

5.2.1. Chuẩn bị công cụ

5.2.2. Cấu hình quyền truy cập AWS

Hạ tầng dự án được phân quyền dựa trên nguyên tắc đặc quyền tối thiểu (Least Privilege) với các thành phần chính:

  • AWS IAM Identity Center: Quản lý quyền truy cập tập trung vào tài khoản AWS thông qua xác thực Single Sign-On (SSO).
  • Permission set nutrition-plan: Chỉ gồm chính sách ReadOnlyAccess của AWS, dùng để kiểm tra cú pháp, validate và lập kế hoạch thực thi (terraform plan).
  • Permission set nutrition-apply: Gồm chính sách ReadOnlyAccess kết hợp cùng Inline Policy nutrition-apply-policy.json để triển khai tài nguyên được phê duyệt.
  • Chính sách nutrition-boundary: Đóng vai trò trần quyền tối đa (Permission Boundary) cho toàn bộ IAM Role do Terraform khởi tạo (ECS Task Role, Execution Role, GitHub Actions OIDC Role).

Các bước cấu hình và xác minh trong IAM Identity Center (theo docs/aws-setup/README.md):

  1. Đăng nhập AWS Management Console với tài khoản quản trị (Root hoặc Admin).
  2. Mở IAM Policies và tạo chính sách nutrition-boundary từ file docs/aws-setup/nutrition-boundary-policy.json. Kiểm tra Access Analyzer / Policy Validation không báo lỗi cú pháp.
  3. Mở IAM Identity Center → Permission sets:
    • Tạo permission set nutrition-plan với AWS managed policy ReadOnlyAccess.
    • Tạo permission set nutrition-apply với ReadOnlyAccess và dán nội dung từ docs/aws-setup/nutrition-apply-policy.json vào Inline policy. Thời hạn phiên (Session duration) thiết lập 4 giờ.
  4. Gán (Assign) cả hai permission set trên cho người dùng trên tài khoản AWS đích.
  5. Xác minh các ngoại lệ theo Region: Toàn bộ dịch vụ dự án giới hạn tại ap-southeast-1 (Singapore); CloudFront là dịch vụ toàn cầu và S3 giới hạn theo tên bucket nutrition-*; ngoại lệ ap-northeast-1 (Tokyo) được mở riêng cho Amazon Bedrock và Guardrails.

Lưu ý bảo mật: Tuyệt đối không cấp quyền AdministratorAccess không giới hạn. Dự án sử dụng Permission Boundary để khóa trần quyền và ngăn chặn việc gán quyền leo thang ngoài ý muốn.

5.2.3. Đăng nhập AWS CLI bằng SSO

Đăng nhập vào phiên làm việc SSO qua cấu hình session nutrition đã thiết lập trên AWS CLI:

PowerShell
aws sso login --sso-session nutrition

Sau khi trình duyệt xác thực thành công, xác minh danh tính đang hoạt động bằng profile nutrition-plan:

PowerShell
aws sts get-caller-identity --profile nutrition-plan

Kết quả mong đợi: Lệnh trả về cấu trúc JSON hợp lệ chứa các trường UserId, Account và Arn tương ứng với permission set đang đăng nhập. (Để đảm bảo nguyên tắc bảo mật, thông tin Account ID và Arn thực tế được bảo vệ và không đưa vào tài liệu công khai).

Xử lý lỗi InvalidGrantException: Lỗi này xuất hiện khi token của phiên SSO đã hết thời hạn hợp lệ. Thực hiện đăng nhập lại bằng lệnh aws sso login --sso-session nutrition để cấp token mới.

5.2.4. Khởi tạo Terraform Backend trên S3

Terraform State lưu trữ toàn bộ trạng thái tài nguyên AWS do Terraform quản lý. Dự án sử dụng Amazon S3 làm Remote Backend với mã hóa tĩnh SSE-S3 (AES256), bật tính năng kiểm soát phiên bản (Versioning) và khóa trạng thái đồng thời bằng tham số native use_lockfile = true của Terraform 1.10+.

Các bước thực hiện theo hướng dẫn tại infra/README.md:

1 Khởi tạo Terraform Bootstrap

Di chuyển vào thư mục bootstrap và tải AWS provider:

PowerShell
terraform -chdir=infra/bootstrap init
2 Kiểm tra Terraform Plan

Gán biến định danh người sở hữu và xuất bản kế hoạch triển khai ra file nhị phân:

PowerShell
$env:TF_VAR_owner = "your-name"
terraform -chdir=infra/bootstrap plan -out=tfplan

Người học đọc kỹ danh sách tài nguyên S3 bucket dự kiến tạo và kiểm tra không có tài nguyên lạ trước khi thực hiện apply.

3 Triển khai Bootstrap

Chuyển sang profile nutrition-apply để áp dụng bản kế hoạch:

PowerShell
$env:AWS_PROFILE = "nutrition-apply"
terraform -chdir=infra/bootstrap apply tfplan
4 Lấy thông tin State Bucket

Truy vấn tên bucket S3 vừa được tạo từ output của Terraform:

PowerShell
terraform -chdir=infra/bootstrap output state_bucket

Tên bucket có định dạng duy nhất: nutrition-dev-tfstate-<account-id>.

5 Cấu hình Terraform Backend

Sao chép file mẫu backend.hcl.example có sẵn trong thư mục môi trường dev và điền tên bucket thực tế:

PowerShell
cp infra/envs/dev/backend.hcl.example infra/envs/dev/backend.hcl

Nội dung file infra/envs/dev/backend.hcl sau khi điền:

HCL
bucket = "nutrition-dev-tfstate-<account-id>"

Đặc tính bảo vệ của S3 State Backend:

  • Terraform State được lưu trữ an toàn trong bucket S3 với mã hóa phía máy chủ (SSE-S3).
  • Tham số use_lockfile = true kích hoạt cơ chế khóa native của S3, loại bỏ hoàn toàn nguy cơ ghi đè đồng thời mà không cần bảng DynamoDB bổ sung.
  • Bucket được cấu hình prevent_destroy = true trong Terraform bootstrap để bảo vệ khỏi các thao tác xóa nhầm ngoài ý muốn.

Lưu ý về AWS Budgets: Trước khi triển khai các dịch vụ tính phí, người học nên thiết lập ngân sách cảnh báo trên AWS Budgets. Dự án sử dụng mức ngân sách tham chiếu 100 USD. Hướng dẫn chi tiết cấu hình ngân sách, thông báo email và ảnh minh chứng sẽ được trình bày trong bài 5.6 – Giám sát, bảo mật và chi phí. Module bootstrap hiện tại không tạo AWS Budgets tự động.

  • ✓ Bucket lưu trữ Terraform State đã được tạo tại vùng ap-southeast-1 với đầy đủ mã hóa và chặn public access.
  • ✓ File cấu hình infra/envs/dev/backend.hcl trỏ chính xác đến tên bucket thực tế.
  • ✓ Các thông tin nhạy cảm (Account ID thực tế, khóa truy cập) không xuất hiện trong tài liệu hoặc git commit.

5.2.6. Lưu ý và lỗi thường gặp

  • Phiên AWS SSO hết hạn (InvalidGrantException / ExpiredToken): Thực hiện đăng nhập lại bằng lệnh aws sso login --sso-session nutrition để cấp token phiên mới.
  • Lỗi khóa trạng thái (Terraform State Lock): Nếu state bị khóa do phiên apply trước đó bị gián đoạn đột ngột, hãy xác minh kỹ lưỡng không còn bất kỳ tiến trình Terraform nào đang thao tác trên tài nguyên. Chỉ thực hiện lệnh terraform force-unlock <LOCK-ID> khi đã xác minh an toàn và có đủ quyền hạn. Tuyệt đối không xóa file state hoặc bucket lưu trữ.
  • Lỗi quyền AWS không đủ (AccessDeniedException): Kiểm tra biến môi trường $env:AWS_PROFILE xem đã chuyển sang profile nutrition-apply hay chưa. Đối chiếu quyền còn thiếu với tài liệu docs/aws-setup/README.md, không tự ý cấp quyền AdministratorAccess toàn bộ.

5.3 – Hạ tầng cốt lõi

Bài thực hành này hướng dẫn triển khai mạng VPC, cơ sở dữ liệu Amazon RDS PostgreSQL và dịch vụ xác thực Amazon Cognito bằng Terraform. Đây là những thành phần nền tảng để triển khai backend Spring Boot trong các bước tiếp theo.

5.3.1. Tạo mạng VPC

A. Mục tiêu

Triển khai hạ tầng mạng phân vùng phục vụ backend và database, bảo đảm Application Load Balancer (ALB), ECS Fargate và RDS có phạm vi truy cập phù hợp, đồng thời tối ưu chi phí bằng cách loại bỏ NAT Gateway.

B. Kiến trúc mạng

Theo thiết kế của nhóm (Quyết định D15 & D19), hạ tầng mạng bao gồm:

  • Một VPC tại Region Singapore (ap-southeast-1), dải mạng mặc định 10.0.0.0/16 trải rộng trên 2 Availability Zones.
  • Hai Public Subnets (10.0.0.0/24 và 10.0.1.0/24) dành cho ALB và các container ECS Fargate.
  • Hai Private Database Subnets (10.0.100.0/24 và 10.0.101.0/24) dành riêng cho Amazon RDS, hoàn toàn không có route ra Internet.
  • Một Internet Gateway (IGW) kết nối VPC với mạng Internet công cộng.
  • Bảng định tuyến (Route Tables): Bảng public trỏ 0.0.0.0/0 ra IGW; bảng database chỉ định tuyến nội bộ VPC.
  • S3 Gateway Endpoint: Cho phép ECS task truyền nhận dữ liệu với Amazon S3 (ảnh sản phẩm) qua mạng nội bộ AWS hoàn toàn miễn phí, không đi qua Internet Gateway.
  • Managed Prefix List của CloudFront: Chỉ cho phép các dải địa chỉ IP xuất phát từ CloudFront truy cập vào ALB.

Phân tách Security Groups 3 lớp độc lập:

  • ALB Security Group (nutrition-dev-alb): Ingress chỉ nhận HTTP (cổng 80) từ CloudFront Managed Prefix List; Egress chỉ chuyển tiếp tới Security Group của ECS trên cổng 8080.
  • ECS Security Group (nutrition-dev-ecs): Ingress chỉ nhận lưu lượng ứng dụng (cổng 8080) từ ALB SG; Egress cho phép cổng 5432 tới RDS SG và HTTPS (cổng 443) ra ngoài để gọi ECR, Bedrock, Cognito JWKS và CloudWatch.
  • RDS Security Group (nutrition-dev-rds): Ingress chỉ cho phép kết nối PostgreSQL (cổng 5432) duy nhất từ ECS SG; nghiêm cấm mọi truy cập từ Internet.

C. Các bước thực hành

1 Kiểm tra cấu hình Terraform Network

Mở file infra/modules/network/main.tf để kiểm tra khai báo prefix list của CloudFront và định tuyến S3 Gateway Endpoint:

HCL
data "aws_ec2_managed_prefix_list" "cloudfront" {
  name = "com.amazonaws.global.cloudfront.origin-facing"
}

Đoạn mã trên đảm bảo ALB chỉ chấp nhận các gói tin được định tuyến qua mạng phân phối CDN của CloudFront.

2 Kiểm tra Terraform Variables

Đối chiếu các biến đầu vào từ infra/envs/dev/main.tf được truyền cho module network:

  • name_prefix = "nutrition-dev": Tiền tố định danh tài nguyên thống nhất.
  • enable_nat = false: Mặc định tắt NAT Gateway để tiết kiệm chi phí vận hành (~32 USD/tháng). ECS Fargate sẽ sử dụng Public IP trong Public Subnet để giao tiếp ra các API của AWS.
3 Kiểm tra Terraform Plan

Sử dụng profile nutrition-plan đã chuẩn bị ở Bài 5.2 để kiểm tra kế hoạch triển khai tài nguyên:

PowerShell
$env:AWS_PROFILE = "nutrition-plan"
terraform -chdir=infra/envs/dev init
terraform -chdir=infra/envs/dev plan -var="app_running=false" -out=tfplan

Người học đọc kỹ danh sách tài nguyên mạng dự kiến được tạo: 1 VPC, 4 Subnets, 1 Internet Gateway, 2 Route Tables, 3 Security Groups và 1 VPC Endpoint.

4 Triển khai hạ tầng (Apply)

Chuyển sang profile nutrition-apply và áp dụng bản kế hoạch vừa kiểm tra:

PowerShell
$env:AWS_PROFILE = "nutrition-apply"
terraform -chdir=infra/envs/dev apply tfplan

Lưu ý kiến trúc: Root module tại infra/envs/dev/main.tf quản lý đồng bộ toàn bộ tài nguyên nền tảng. Khi chạy apply, Terraform sẽ triển khai đồng thời cả mạng VPC, cơ sở dữ liệu RDS và Cognito (ở trạng thái chờ app_running = false). Không nên sử dụng cờ -target vì có thể gây sai lệch phụ thuộc state.

Đăng nhập AWS Management Console, điều hướng tới VPC → Your VPCs và kiểm tra:

5.3.2. Tạo cơ sở dữ liệu Amazon RDS

A. Mục tiêu

Triển khai hệ quản trị cơ sở dữ liệu quan hệ PostgreSQL 17 trên Amazon RDS, thiết lập cô lập bảo mật tuyệt đối và tự động hóa quản lý lược đồ dữ liệu bằng Flyway.

B. Cấu hình cơ sở dữ liệu

Bảng thông số kỹ thuật của Amazon RDS PostgreSQL trong môi trường dev:

Thuộc tínhGiá trị cấu hình
Dịch vụAmazon RDS for PostgreSQL (Engine version 17.x)
Instance Classdb.t4g.micro (Kiến trúc AWS Graviton2 ARM, tối ưu chi phí)
Storage20 GB gp3 (Hỗ trợ autoscaling tối đa 100 GB)
AvailabilitySingle-AZ (mặc định tiết kiệm chi phí demo, hỗ trợ chuyển Multi-AZ qua biến rds_multi_az)
Phân vùng mạngPrivate database subnets (nutrition-dev-db)
Truy cập công khaiTắt hoàn toàn (publicly_accessible = false)
Mã hóa dữ liệuBật mã hóa tĩnh với AWS KMS (storage_encrypted = true)
Quản lý xác thựcAWS Secrets Manager tự sinh và xoay vòng mật khẩu (manage_master_user_password = true)
Quản lý Lược đồFlyway migrations V1–V11 tích hợp sẵn trong Spring Boot

Đặc tính bảo vệ chính:

  • RDS không thể bị truy cập trực tiếp từ Internet, ngăn chặn hoàn toàn nguy cơ rò rỉ dữ liệu qua tấn công mạng công cộng.
  • Security Group chỉ chấp nhận kết nối qua cổng PostgreSQL tiêu chuẩn (5432) từ các ECS tasks mang nhãn nutrition-dev-ecs.
  • Mật khẩu master được tạo tự động bởi Secrets Manager, không bao giờ xuất hiện dưới dạng văn bản thô (plaintext) trong code hay state file.
  • Flyway đảm bảo tính bất biến và đồng bộ phiên bản của cấu trúc cơ sở dữ liệu.

C. Các bước thực hành

1 Kiểm tra Terraform RDS Module

Mở infra/modules/rds/main.tf và đối chiếu các thiết lập bảo mật cốt lõi:

HCL
manage_master_user_password = true

db_subnet_group_name   = aws_db_subnet_group.main.name
vpc_security_group_ids = [var.security_group_id]
publicly_accessible    = false
multi_az               = var.multi_az

Thiết lập manage_master_user_password = true kích hoạt tính năng tích hợp trực tiếp với Secrets Manager của RDS mà không cần quản lý secret thủ công.

2 Kiểm tra DB Subnet Group và Security Group

Đảm bảo tài nguyên aws_db_subnet_group.main liên kết đầy đủ 2 subnet ID thuộc vùng private và gắn đúng Security Group ID của RDS từ module network.

3 Triển khai qua Terraform

Cơ sở dữ liệu RDS đã được tạo tự động khi áp dụng kế hoạch tại thư mục infra/envs/dev trong Bước 4 của mục 5.3.1. Quá trình tạo RDS PostgreSQL thường mất khoảng 5–8 phút.

Khi backend Spring Boot khởi chạy trên ECS, Flyway sẽ tự động kiểm tra bảng flyway_schema_history và thực thi tuần tự các migration chưa áp dụng.

5.3.3. Cấu hình Amazon Cognito

A. Mục tiêu

Xây dựng hệ thống nhận thực người dùng tập trung, cấp phát mã thông báo JWT và phân quyền truy cập ứng dụng theo vai trò (Role-Based Access Control).

B. Cấu hình Cognito

Theo thiết kế bảo mật của hệ thống:

  • User Pool (nutrition-dev-users): Định danh người dùng bằng địa chỉ Email; kích hoạt tự động gửi mã xác thực email; áp dụng chính sách mật khẩu mạnh (tối thiểu 8 ký tự, có ký tự in hoa, in thường, chữ số và ký tự đặc biệt).
  • App Client (nutrition-dev-spa): Dành cho ứng dụng Single Page Application (React SPA), cấu hình generate_secret = false vì ứng dụng chạy phía trình duyệt của người dùng không thể giữ bí mật Client Secret.
  • Luồng xác thực: Sử dụng giao thức Secure Remote Password (ALLOW_USER_SRP_AUTH) và làm mới phiên qua ALLOW_REFRESH_TOKEN_AUTH. Không sử dụng Cognito Hosted UI mà tích hợp giao diện đăng nhập trực tiếp trong React.
  • Nhóm người dùng (User Groups): Thiết lập 2 nhóm chính gồm USER (khách hàng tiêu dùng) và ADMIN (quản trị viên cửa hàng).
  • Xác thực phía Backend: Spring Boot Resource Server kiểm tra chữ ký số của JWT token thông qua JWKS endpoint của Cognito, giải mã định danh người dùng từ claim sub và phân quyền hạn từ claim cognito:groups.

C. Các bước thực hành

1 Kiểm tra Cognito Terraform Module

Mở infra/modules/cognito/main.tf để xem định nghĩa User Pool, App Client và thiết lập khôi phục tài khoản qua email:

HCL
resource "aws_cognito_user_pool_client" "spa" {
  name            = "${var.name_prefix}-spa"
  user_pool_id    = aws_cognito_user_pool.users.id
  generate_secret = false

explicit_auth_flows = [
“ALLOW_USER_SRP_AUTH”,
“ALLOW_REFRESH_TOKEN_AUTH”,
“ALLOW_ADMIN_USER_PASSWORD_AUTH”,
]
}

2 Kiểm tra các nhóm USER và ADMIN

Khai báo nhóm người dùng trong infra/modules/cognito/main.tf:

HCL
resource "aws_cognito_user_group" "admin" {
  name         = "ADMIN"
  user_pool_id = aws_cognito_user_pool.users.id
}

resource “aws_cognito_user_group” “user” {
name         = “USER”
user_pool_id = aws_cognito_user_pool.users.id
}

Người dùng sau khi đăng ký sẽ được gán vào nhóm USER. Chỉ những tài khoản được chỉ định trong nhóm ADMIN mới có quyền truy cập vào các API quản lý sản phẩm và đơn hàng.

3 Triển khai Cognito

Module Cognito được quản lý hoàn toàn bằng mã nguồn Terraform và đã được áp dụng trong lệnh apply tổng thể. Tuyệt đối không tạo User Pool thủ công qua Console để tránh tình trạng lệch trạng thái (drift state).

4 Kiểm tra trên AWS Console

Điều hướng tới Amazon Cognito → User pools và chọn nutrition-dev-users. Xác minh:

  • User Pool ID có tiền tố dạng ap-southeast-1_....
  • Tại thẻ App integration → App clients: Có client nutrition-dev-spa với thiết lập Client secret: No client secret.
  • Tại thẻ Groups: Xuất hiện đầy đủ 2 nhóm ADMIN và USER.
5 Kiểm tra phân quyền API (theo docs/demo.md)

Xác nhận cơ chế bảo vệ phân quyền của backend Spring Boot đối với các lệnh gọi API:

  • Yêu cầu không có Token: Gửi request tới các endpoint được bảo vệ mà thiếu header Authorization: Bearer <token> → Backend lập tức từ chối và phản hồi HTTP 401 Unauthorized.
  • Khách hàng thông thường (USER) gọi API quản trị: Tài khoản thuộc nhóm USER gọi các endpoint /api/admin/** → Backend kiểm tra claim cognito:groups và phản hồi HTTP 403 Forbidden.
  • Quản trị viên (ADMIN): Xác thực thành công và được phép thao tác toàn quyền trên các API quản lý.

3. Các bước thực hành chi tiết

1 Đóng gói Backend Spring Boot và đẩy Docker Image lên ECR

Mở terminal tại thư mục gốc của repository, build file JAR và đóng gói container ARM64:

Terminal
# 1. Di chuyển vào thư mục backend và build file JAR
cd backend
./mvnw clean package -DskipTests

2. Lấy URL của ECR Repository


cd ../infra/envs/dev
ECR_URL=$(terraform output -raw ecr_repository_url)
cd ../../../backend


3. Đăng nhập Docker CLI vào ECR Registry


aws ecr get-login-password –region ap-southeast-1 | docker login –username AWS –password-stdin $ECR_URL


4. Build Docker container image cho kiến trúc linux/arm64


docker build –platform linux/arm64 -t $ECR_URL:latest .


5. Đẩy image lên ECR


docker push $ECR_URL:latest

Sau khi đẩy xong, Amazon ECR sẽ tự động quét bảo mật (scan-on-push) để rà soát các lỗ hổng CVE tiềm ẩn trong image.

2 Bật hạ tầng ứng dụng và khởi động ECS Task

Chuyển sang thư mục infra/envs/dev và chạy apply với biến app_running=true:

Terminal
cd ../infra/envs/dev
terraform apply -var="app_running=true" -var="api_desired_count=1" -auto-approve

Thao tác này sẽ thực hiện:

  • Khởi động instance Amazon RDS PostgreSQL từ trạng thái stopped sang available.
  • Tạo Application Load Balancer (ALB), Target Group, Listener Rules và Custom Header X-Origin-Verify.
  • Tạo ECS Task Definition và kích hoạt ECS Fargate Service chạy 1 active task kéo image :latest từ ECR.
  • Chạy Flyway migrations tự động nạp 152 sản phẩm và hồ sơ dinh dưỡng USDA vào cơ sở dữ liệu.
3 Build và Deploy Frontend React lên Amazon S3

Biên dịch frontend React 19 và tải lên S3 bucket, sau đó xóa cache CloudFront Edge PoPs:

Terminal
cd ../../../frontend
npm install
npm run build

Lấy tên Bucket và Distribution ID từ terraform output


cd ../infra/envs/dev
FRONTEND_BUCKET=$(terraform output -raw frontend_bucket_name)
DIST_ID=$(terraform output -raw cloudfront_distribution_id)
cd ../../../frontend


Đồng bộ file build lên S3


aws s3 sync dist/ s3://$FRONTEND_BUCKET/ –delete


Làm mới cache CloudFront toàn cầu


aws cloudfront create-invalidation –distribution-id $DIST_ID –paths “/*"

3. Các bước thực hành chi tiết

1 Kích hoạt Model Access trên Amazon Bedrock Console

Đăng nhập AWS Management Console, chuyển vùng sang Tokyo (ap-northeast-1):

  1. Truy cập dịch vụ Amazon Bedrock → Chọn mục Model access ở menu bên trái.
  2. Nhấp nút Modify model access.
  3. Tìm nhà cung cấp Amazon và tích chọn mô hình Amazon Nova 2 Lite (hoặc inference profile jp.amazon.nova-lite-v1:0).
  4. Nhấp Next và Submit để hoàn tất cấp quyền truy cập (thường được phê duyệt tức thì).
2 Cấu hình Bedrock Guardrails trong Terraform

Hạ tầng Terraform của dự án đã tích hợp sẵn module infra/modules/guardrail để bảo vệ an toàn nội dung. Kiểm tra cấu hình trong infra/envs/dev/terraform.tfvars:

terraform.tfvars
bedrock_region               = "ap-northeast-1"
bedrock_model_id             = "amazon.nova-lite-v1:0"
bedrock_inference_profile_id = "jp.amazon.nova-lite-v1:0"
guardrail_tier               = "STANDARD"

Cấu hình này thiết lập các bộ lọc:

  • Content Filters: Chặn các nội dung thù ghét, bạo lực và hành vi độc hại với ngưỡng HIGH.
  • Sensitive Information Filters: Ngăn chặn việc làm lộ số thẻ tín dụng, mật khẩu hay dữ liệu cá nhân.
  • Topic Deny: Ngăn AI đưa ra các phác đồ điều trị bệnh lý hoặc chẩn đoán thay thế bác sĩ (tuân thủ Medical Disclaimer).
3 Phân tích luồng xử lý AI trong Spring Boot Backend

Backend Spring Boot 4 gọi Bedrock Converse API với prompt định chuẩn để trích xuất JSON có cấu trúc:

Java / Spring Boot Logic
// 1. Nhận câu hỏi tự nhiên: "tìm bữa tối dưới 500 calo giàu protein không có gluten"
// 2. Gửi request đến Bedrock Nova 2 Lite (Tokyo) với Guardrail ID
ConverseResponse response = bedrockClient.converse(req -> req
    .modelId("jp.amazon.nova-lite-v1:0")
    .guardrailConfig(g -> g.guardrailIdentifier(guardrailId).guardrailVersion(guardrailVer))
    .messages(userMessage)
);

// 3. AI trả về kết quả JSON tham số lọc (Parameter Extraction):
// { “maxCalories”: 500, “minProtein”: 25, “excludedAllergens”: [“GLUTEN”] }


// 4. Backend dùng JPA Specification / SQL truy vấn trực tiếp bảng products trong PostgreSQL:
// SELECT * FROM products WHERE calories <= 500 AND protein >= 25 AND NOT (‘GLUTEN’ = ANY(allergens));

4 Kiểm thử thực tế API tra cứu dinh dưỡng

Thực hiện gọi API kiểm thử từ dòng lệnh để xác minh chức năng:

Terminal
curl -X POST "https:///api/ai/nutrition-lookup"   -H "Content-Type: application/json"   -d '{"query": "gợi ý món ăn ít carb dưới 350 calo cho người tập gym"}'

Kết quả JSON trả về danh sách các món ăn thực tế (ví dụ: Salad ức gà áp chảo, Thịt bò phi lê nướng măng tây) kèm số liệu calo và macro chuẩn xác từ cơ sở dữ liệu USDA.

4. Kết quả mong đợi & Xác minh

  • AI nhận diện chính xác các từ khóa dinh dưỡng và chuyển đổi thành bộ lọc SQL hợp lệ.
  • Khi người dùng cố tình hỏi câu hỏi độc hại hoặc yêu cầu kê đơn thuốc, Bedrock Guardrail sẽ chặn và trả về thông báo: "Yêu cầu không phù hợp với chính sách an toàn thông tin dinh dưỡng của hệ thống."

5. Lỗi thường gặp & Cách xử lý

  • Lỗi "AccessDeniedException: You don't have access to the model": Bạn chưa kích hoạt Model Access trên AWS Console ở vùng Tokyo (ap-northeast-1). Hãy vào Bedrock Console Tokyo để yêu cầu quyền truy cập.
  • Lỗi "ValidationException: Guardrail not found": Guardrail ID chưa khớp hoặc chưa được tạo. Hãy chạy lệnh terraform apply để Terraform hoàn tất việc provisioning module guardrail.

3 Kiểm tra CloudWatch Alarms

Các chỉ số cảnh báo được khởi tạo sẵn trong Terraform:

  • ALB 5XX Errors: Cảnh báo khi tỷ lệ lỗi máy chủ vượt 1% trong 5 phút.
  • ECS CPU Utilization: Cảnh báo khi mức sử dụng CPU của container vượt 80%.
  • ECS Memory Utilization: Cảnh báo khi RAM vượt 85%.
  • RDS Free Storage Space: Cảnh báo khi dung lượng ổ cứng gp3 còn dưới 2 GB.

3. Các bước thực hành chi tiết

1 Sao lưu Snapshot cơ sở dữ liệu cuối cùng (Tùy chọn)

Nếu bạn muốn lưu trữ lại toàn bộ dữ liệu đơn hàng và sản phẩm phục vụ cho tương lai:

Terminal
aws rds create-db-snapshot   --db-instance-identifier nutrition-dev-postgres   --db-snapshot-identifier nutrition-dev-final-backup   --region ap-southeast-1
2 Làm rỗng các S3 Buckets

AWS không cho phép xóa các bucket S3 nếu bên trong vẫn còn chứa tệp tin hoặc các version cũ. Hãy làm rỗng nội dung các buckets trước:

Terminal
# Lấy danh sách tên bucket từ terraform output
cd infra/envs/dev
FRONTEND_BUCKET=$(terraform output -raw frontend_bucket_name)
IMAGES_BUCKET=$(terraform output -raw images_bucket_name)

Xóa toàn bộ tệp trong các bucket


aws s3 rm s3://$FRONTEND_BUCKET/ –recursive
aws s3 rm s3://$IMAGES_BUCKET/ –recursive

3 Hủy toàn bộ hạ tầng Dev bằng Terraform Destroy

Thực thi lệnh hủy diệt toàn bộ hạ tầng đám mây đã tạo:

Terminal
terraform destroy -auto-approve

Quá trình này sẽ giải phóng CloudFront distribution, ALB, ECS service/task, RDS instance, ECR repository, Cognito User Pool, VPC và các Security Groups.

4 Hủy Terraform Bootstrap State Bucket

Xóa nốt S3 bucket lưu trữ state file ở thư mục bootstrap:

Terminal
cd ../bootstrap
# Lấy tên state bucket và xóa
TF_STATE_BUCKET=$(terraform output -raw state_bucket_name)
aws s3 rm s3://$TF_STATE_BUCKET/ --recursive
terraform destroy -auto-approve
5 Kiểm tra xác minh trên AWS Management Console

Đăng nhập AWS Console và kiểm tra lần lượt các dịch vụ tại vùng Singapore (ap-southeast-1):

  • Amazon ECS: Clusters rỗng, không còn Task nào chạy ngầm.
  • Amazon RDS: Databases rỗng (chỉ còn final snapshot nếu bạn chủ động giữ lại).
  • Amazon EC2: Load Balancers và Target Groups đã bị xóa; không có Elastic IP nào bị giữ lại mà không gắn vào instance.
  • Amazon VPC: Không còn NAT Gateway nào đang chạy.
  • CloudFront: Distribution đã bị vô hiệu hóa hoặc xóa hoàn toàn.
