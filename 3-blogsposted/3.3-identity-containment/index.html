EC2 ISOLATION DOES NOT MEAN THE ATTACKER IS ISOLATED

Beyond Network Isolation: Rethinking Identity Containment on AWS
View post on AWS Study Group VN community
15/11/2026
Figure 1: Automated Incident Response architecture on AWS – Combining Network Containment, Credential Issuance Containment, and Identity Containment.

What happens if an EC2 instance is completely isolated from the network, yet an attacker can still access your AWS resources? An in-depth architectural analysis of Network Containment versus Identity Containment: why Security Groups cannot terminate active IAM sessions, the limitations of IMDSv2 against remote code execution, and designing an automated incident response workflow combining GuardDuty, EventBridge, Lambda runbooks, and aws:EC2InstanceSourceVPC condition keys.

1. When What Is Stolen Is Not Just Data, But Identity

Consider an enterprise deploying its backend workload on Amazon EC2, using Amazon S3 for durable object storage and Amazon DynamoDB for transactional state.

Rather than embedding long-lived Access Keys into source code, EC2 is attached to an IAM Role via an Instance Profile, consuming Temporary Security Credentials issued dynamically by the Instance Metadata Service (IMDS).

While this aligns with AWS security best practices, examine this realistic incident timeline:

TimeEvent / ActionTechnical Implication & State
09:00EC2 Host CompromiseAttacker exploits an application vulnerability to achieve arbitrary remote code execution (RCE) on the host.
09:05Credentials ExfiltrationAttacker queries IMDS and extracts temporary security tokens (AccessKey, SecretKey, SessionToken).
09:10Security Team Detects AnomalySecurity operations center (SOC) detects suspicious host behavior or unexpected API calls.
09:15Quarantine Security Group AppliedEC2 is isolated at the network layer by stripping standard inbound and outbound traffic rules.
09:20Attacker Accesses S3 from OutsideFrom an external Internet environment, the attacker successfully dispatches requests to Amazon S3 using the stolen credentials.
Why does this happen?

Because Temporary Credentials are not inherently bound to the network origin of the EC2 instance that received them. As long as the credentials have not expired and access has not been denied by security policies, an attacker can exploit the workload identity directly against AWS APIs without needing any ongoing network connection to the original EC2 instance.

2. Network Containment ≠ Identity Containment

A critical pitfall in cloud incident response is failing to distinguish between two distinct control planes: Network Containment (isolating resources at the network perimeter) and Identity Containment (governing and revoking the operational permissions of compromised identities).

Control LayerMechanismCapabilityCore Limitation
Network Containment
Network Layer		Quarantine Security Group, NACLs, Private SubnetsBlocks network ingress/egress to and from the EC2 instanceCannot invalidate active IAM credentials; does not drop tracked stateful connections immediately.
Identity Containment
Identity Layer (IAM)		Revoke Active Sessions, Policy Denials, Detach Instance ProfileRevokes operational validity of temporary STS credentialsWithout detaching the Instance Profile, the instance can immediately request new credentials from IMDS.

Security Groups filter network ingress and egress traffic, but possess zero awareness or authority over IAM sessions. Furthermore, modifying a Security Group does not automatically terminate existing tracked stateful TCP connections.

Private Subnets prevent direct inbound connections from the public Internet, but do not protect against an attacker utilizing exfiltrated credentials from an external machine.

Even IMDSv2, while highly effective against Server-Side Request Forgery (SSRF) exploits, offers no protection once an attacker has established arbitrary code execution on the instance.

Each security mechanism addresses a different failure domain. Stacking security tools without understanding their architectural boundaries does not produce a secure architecture.

3. If Credentials Are Stolen, Can We Render Them Useless Out of Context?

AWS provides Global Condition Keys that enable organizations to restrict credential usage based on operational context, verifying that request attributes match the issuance environment:

  • aws:EC2InstanceSourceVPC: Enforces that requests must originate from the exact VPC where the EC2 instance was granted credentials.
  • aws:EC2InstanceSourcePrivateIPv4: Verifies the private IPv4 address assigned to the instance when the credentials were issued.
  • aws:SourceVpc: Checks whether the request passed through a specific VPC Endpoint when accessing AWS service APIs.
  • aws:VpcSourceIp: Validates the source IP address within the private VPC network space.

In the illustrated architecture, EC2 resides within a Private Subnet and connects to Amazon S3 and DynamoDB via dedicated Gateway Endpoints.

By authoring IAM Policies that compare credential issuance context with runtime request context, we can deny unauthorized requests originating outside the legitimate network boundary, even when the security token is valid.

Example: IAM Policy Deny access outside source VPC (Context-Aware Enforcement)
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EnforceVpcSourceContext",
      "Effect": "Deny",
      "Action": ["s3:*", "dynamodb:*"],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:EC2InstanceSourceVPC": "vpc-0123456789abcdef0"
        }
      }
    }
  ]
}

However, architects must keep in mind that not all AWS APIs utilize VPC Endpoints. Overly restrictive policies can break legitimate operational workloads.

This mechanism also does not prevent malicious actions carried out directly on the compromised EC2 instance itself.

This is why a robust cloud security strategy demands layered Defense in Depth.

4. When Security Remediation Causes Operational Outages

AWS IAM provides an Active Session Revocation mechanism using the managed AWSRevokeOlderSessions policy and the aws:TokenIssueTime condition to deny requests from credentials issued prior to a specific cutoff timestamp.

However, imagine a production fleet where 10 EC2 instances share a single IAM Role, but only one instance has been compromised.

Executing a blanket session revocation on that IAM Role immediately disrupts all 9 healthy instances, inducing a widespread cascading outage.

Furthermore, Revoke Active Sessions does not stop the compromised EC2 from immediately querying IMDS for fresh credentials. Therefore, security teams must detach or swap the Instance Profile with a restricted quarantine profile.

At this point, engineering teams confront the delicate trade-off between Security and Availability.

This demonstrates that IAM architecture is not just about granting Least Privilege, but equally about strictly limiting the Blast Radius when an incident occurs.

5. Architectural Approach on AWS

Synthesizing the architecture diagram, we can construct an Automated Incident Response workflow as follows:

AWS ServiceRole in Incident Response
AWS CloudTrailCaptures and records AWS API activity. Data Events must be enabled on S3 and DynamoDB for granular data-tier visibility.
Amazon GuardDutyContinuously monitors security data sources to detect anomalous credential usage (e.g. InstanceCredentialExfiltration.OutsideAWS finding).
Amazon EventBridgeMatches GuardDuty finding event patterns and triggers automated incident response handlers.
AWS LambdaExecutes an AWS Systems Manager Automation runbook to carry out multi-tiered containment actions.

The containment workflow executes across three synchronized action tiers:

  • Network Containment: Attaches a Quarantine Security Group and inspects existing stateful connections.
  • Credential Issuance Containment: Detaches or swaps the Instance Profile to prevent the instance from receiving fresh privileged credentials.
  • Identity Containment: Revokes active IAM Role sessions and verifies policy propagation across AWS endpoints.

In production environments, actions that carry high operational disruption risks should be governed by appropriate approval workflows. The ultimate goal is not simply deploying more tools, but ensuring that each defensive layer successfully contains damage when another layer fails.

Key Takeaway

An AWS Incident Response workflow must govern both Network Containment and Identity Containment simultaneously. Isolating EC2 only solves part of the problem if the operational permissions of the compromised identity have not been revoked.

Because in cloud environments, an attack may begin on a host but propagates through identity abuse.
