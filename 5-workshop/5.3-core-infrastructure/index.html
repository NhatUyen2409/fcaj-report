Technical Workshop Guide

Deploying Personalized Nutrition E-Commerce Platform on AWS

Hands-on Deployment Guide: Spring Boot 4, React 19, ECS Fargate, RDS PostgreSQL, Bedrock AI & Terraform

A comprehensive step-by-step practical lab guide enabling engineers and students to deploy an end-to-end cloud-native nutrition e-commerce platform on Amazon Web Services. The entire infrastructure is automated via Terraform, running containerized Spring Boot 4 backend on serverless ECS Fargate, managed PostgreSQL on RDS, and generative AI intent parsing with Amazon Bedrock Nova 2 Lite.

5.1. Workshop Overview

Building a Personalized Nutrition E-Commerce Platform on AWS

This workshop guides you through deploying a cloud-native nutrition e-commerce platform on AWS using React, Spring Boot, and PostgreSQL, integrated with Amazon Bedrock for natural language food search.

Learners will practice provisioning infrastructure, deploying application workloads, integrating AI capabilities, monitoring systems, and managing AWS cloud costs.

Workshop Objectives

  • Understand cloud web application architecture on AWS.
  • Deploy frontend, backend, and managed database tiers.
  • Integrate Amazon Bedrock for AI-assisted nutritional queries.
  • Establish monitoring, security controls, and cost optimization.

Overall Architecture

Overall Architecture Diagram of Nutrition E-Commerce on AWS.

The React application is distributed globally via CloudFront and S3. API requests are routed through an Application Load Balancer to Spring Boot on ECS Fargate. PostgreSQL is hosted on Amazon RDS, Cognito manages user authentication, and Amazon Bedrock powers nutritional intent extraction. Core application infrastructure is hosted in Singapore, with Bedrock and Guardrails operating in Tokyo.

Workshop Roadmap

  • 5.2. Prerequisites: Prepare AWS Account and developer toolchain.
  • 5.3. Core Infrastructure: Provision cloud resources using Terraform.
  • 5.4. Application Deployment: Deploy React and Spring Boot to AWS.
  • 5.5. Amazon Bedrock: Integrate AI conversational nutrition search.
  • 5.6. Monitoring & Cost: Configure observability, security, and budgets.
  • 5.7. Resource Cleanup: Stop or tear down resources after the workshop.

Expected Outcome

Upon completing this workshop, learners will be capable of deploying, operating, and testing an AI-enabled nutrition e-commerce system on AWS while understanding how to monitor and control cloud expenditures.

5.2.2. Configure AWS Access & IAM

Infrastructure provisioning adheres strictly to the Least Privilege principle with the following IAM components:

  • AWS IAM Identity Center: Centrally manages user authentication and role assignments to AWS accounts via Single Sign-On (SSO).
  • Permission set nutrition-plan: Attached with AWS managed policy ReadOnlyAccess, used for daily inspection, syntax validation, and planning (terraform plan).
  • Permission set nutrition-apply: Combines ReadOnlyAccess with an inline policy from nutrition-apply-policy.json to apply approved infrastructure changes.
  • Policy nutrition-boundary: Enforces a maximum permission boundary (nutrition-boundary-policy.json) on all IAM roles generated by Terraform (ECS task roles, execution roles, GitHub Actions OIDC roles).

Configuration and Verification Steps (per docs/aws-setup/README.md):

  1. Log in to the AWS Management Console with administrative privileges (Root or Admin).
  2. Open IAM Policies and create policy nutrition-boundary pasting docs/aws-setup/nutrition-boundary-policy.json. Verify that Access Analyzer reports zero validation errors.
  3. Open IAM Identity Center → Permission sets:
    • Create permission set nutrition-plan attaching AWS managed policy ReadOnlyAccess.
    • Create permission set nutrition-apply attaching ReadOnlyAccess and pasting docs/aws-setup/nutrition-apply-policy.json into the Inline Policy. Set session duration to 4 hours.
  4. Assign both permission sets to your designated IAM Identity Center user on the target AWS account.
  5. Verify regional isolation constraints: Core services are restricted to ap-southeast-1 (Singapore); CloudFront is global and S3 is restricted to nutrition-* buckets; an exception in ap-northeast-1 (Tokyo) is granted exclusively for Amazon Bedrock and Guardrails.

Security Notice: Never attach unrestricted AdministratorAccess. The project enforces an IAM Permission Boundary to cap maximum permissions and prevent unintended privilege escalation.

5.2.4. Bootstrap Terraform Backend on S3

Terraform State preserves the current state of AWS infrastructure managed by Terraform. The project uses Amazon S3 as a Remote Backend with server-side encryption (SSE-S3 AES256), Versioning enabled, and native state locking via use_lockfile = true (introduced in Terraform 1.10+, eliminating the need for a DynamoDB table).

Follow the step-by-step instructions from infra/README.md:

1 Initialize Terraform Bootstrap

Navigate to the bootstrap directory and download required providers:

PowerShell
terraform -chdir=infra/bootstrap init
2 Review Terraform Plan

Set the owner variable and save the binary execution plan:

PowerShell
$env:TF_VAR_owner = "your-name"
terraform -chdir=infra/bootstrap plan -out=tfplan

Review the planned resources carefully to confirm that only intended S3 state bucket components will be created before proceeding to apply.

3 Deploy Bootstrap

Switch to the nutrition-apply profile and apply the saved plan:

PowerShell
$env:AWS_PROFILE = "nutrition-apply"
terraform -chdir=infra/bootstrap apply tfplan
4 Retrieve State Bucket Name

Query the created S3 state bucket name from Terraform output:

PowerShell
terraform -chdir=infra/bootstrap output state_bucket

The output displays a unique bucket name formatted as: nutrition-dev-tfstate-<account-id>.

5 Configure Dev Environment Backend

Copy the backend template file from the dev environment folder and populate the bucket name:

PowerShell
cp infra/envs/dev/backend.hcl.example infra/envs/dev/backend.hcl

Configured content inside infra/envs/dev/backend.hcl:

HCL
bucket = "nutrition-dev-tfstate-<account-id>"

Key S3 Remote Backend Features:

  • Terraform State is stored securely with server-side encryption (SSE-S3 AES256) and TLS enforcement.
  • use_lockfile = true provides robust native state locking directly on S3 objects, preventing concurrent write collisions.
  • The bucket is protected by prevent_destroy = true in the bootstrap definition to guard against accidental removal.

AWS Budgets Advisory: Prior to deploying chargeable resources, learners should configure budget alert thresholds in AWS Budgets. The team project adheres to a 100 USD benchmark limit. Detailed step-by-step setup, email alerts, and screenshot evidence are covered in Module 5.6 – Monitoring, Security & Cost. Note that the bootstrap module does not automatically create AWS Budgets.

5.2.6. Common Errors & Troubleshooting

  • Expired AWS SSO Session (InvalidGrantException / ExpiredToken): Re-authenticate by running aws sso login --sso-session nutrition to refresh your temporary session token.
  • Terraform State Lock: If state locking errors occur due to an aborted execution, verify that no other terraform processes are active. Only execute terraform force-unlock <LOCK-ID> after ensuring safety and proper permissions. Never manually delete the state bucket or state file.
  • Insufficient AWS Permissions (AccessDeniedException): Check your current active profile via $env:AWS_PROFILE to ensure it is set to nutrition-apply. Compare the missing permissions against docs/aws-setup/README.md; never grant full AdministratorAccess as a workaround.

5.3 – Core Infrastructure

This hands-on lab guides you through provisioning the VPC network, Amazon RDS PostgreSQL database, and Amazon Cognito authentication service using Terraform. These components provide the foundational infrastructure required for deploying the Spring Boot backend in subsequent steps.

5.3.1. VPC Networking

A. Learning Objectives

Deploy segmented network infrastructure for backend services and databases, ensuring Application Load Balancer (ALB), ECS Fargate, and RDS operate within appropriate network boundaries while eliminating NAT Gateway costs.

B. Network Architecture

According to project architectural decisions (D15 & D19), the network comprises:

  • One VPC in Singapore (ap-southeast-1), with default CIDR 10.0.0.0/16 spanned across 2 Availability Zones.
  • Two Public Subnets (10.0.0.0/24 and 10.0.1.0/24) hosting the ALB and ECS Fargate container tasks.
  • Two Private Database Subnets (10.0.100.0/24 and 10.0.101.0/24) dedicated to Amazon RDS with zero direct Internet routing.
  • An Internet Gateway (IGW) attached to the VPC.
  • Route Tables: Public route table directs 0.0.0.0/0 to IGW; database route table restricts traffic strictly to internal VPC CIDRs.
  • S3 Gateway Endpoint: Enables ECS tasks to transfer product media with Amazon S3 over AWS internal network at zero hourly cost, bypassing the Internet Gateway.
  • CloudFront Origin-Facing Managed Prefix List: Restricts ALB ingress exclusively to CloudFront CDN origin-facing IP ranges.

Three-Tier Security Group Isolation:

  • ALB Security Group (nutrition-dev-alb): Ingress accepts HTTP (port 80) only from CloudFront Managed Prefix List; Egress forwards traffic only to ECS tasks on port 8080.
  • ECS Security Group (nutrition-dev-ecs): Ingress accepts application traffic (port 8080) only from ALB SG; Egress allows port 5432 to RDS SG and HTTPS (port 443) outbound to AWS APIs (ECR, Bedrock, Cognito JWKS, CloudWatch).
  • RDS Security Group (nutrition-dev-rds): Ingress permits PostgreSQL traffic (port 5432) strictly from ECS SG; direct Internet ingress is completely forbidden.

C. Step-by-Step Implementation

1 Review Terraform Network Configuration

Inspect infra/modules/network/main.tf to review CloudFront prefix list and S3 gateway endpoint definitions:

HCL
data "aws_ec2_managed_prefix_list" "cloudfront" {
  name = "com.amazonaws.global.cloudfront.origin-facing"
}

This ensures ALB only accepts incoming requests originating from CloudFront edge distributions.

2 Review Terraform Variables

Verify parameters passed into module network from infra/envs/dev/main.tf:

  • name_prefix = "nutrition-dev": Unified naming prefix.
  • enable_nat = false: Disables NAT Gateway by default to prevent hourly billing (~$32/month). ECS tasks assign public IPs in public subnets to communicate outbound with AWS APIs.
3 Generate and Review Terraform Plan

Authenticate with profile nutrition-plan and generate an execution plan:

PowerShell
$env:AWS_PROFILE = "nutrition-plan"
terraform -chdir=infra/envs/dev init
terraform -chdir=infra/envs/dev plan -var="app_running=false" -out=tfplan

Review the staged resources: 1 VPC, 4 Subnets, 1 Internet Gateway, 2 Route Tables, 3 Security Groups, and 1 S3 Gateway Endpoint.

4 Apply Core Infrastructure

Switch to profile nutrition-apply and apply the plan:

PowerShell
$env:AWS_PROFILE = "nutrition-apply"
terraform -chdir=infra/envs/dev apply tfplan

Architecture Note: The dev root module simultaneously provisions network, RDS, and Cognito in an idle state (app_running = false). Do not use -target flags as this can disrupt Terraform state dependency graphs.

5 Verify Resources in AWS Console

Sign in to AWS Console and navigate to VPC → Your VPCs:

  • Confirm VPC nutrition-dev-vpc exists with CIDR 10.0.0.0/16.
  • Confirm 2 Public Subnets and 2 Private DB Subnets across 2 Availability Zones.
  • Confirm Internet Gateway attached to the VPC.
  • Verify DB route table contains no routes toward 0.0.0.0/0.
  • Verify the 3 Security Groups: nutrition-dev-alb, nutrition-dev-ecs, and nutrition-dev-rds.
  • Confirm S3 Gateway Endpoint status is Available.

5.3.2. Amazon RDS PostgreSQL Database

A. Learning Objectives

Provision PostgreSQL 17 on Amazon RDS, enforce zero public exposure, and automate database schema evolution using Flyway migrations.

B. Database Specifications

Amazon RDS PostgreSQL configuration parameters in the dev environment:

PropertyConfigured Value
ServiceAmazon RDS for PostgreSQL (Engine version 17.x)
Instance Classdb.t4g.micro (AWS Graviton2 ARM architecture, cost-optimized)
Storage20 GB gp3 (Autoscaling up to 100 GB)
AvailabilitySingle-AZ (default for demo savings, supports Multi-AZ via rds_multi_az)
Subnet GroupPrivate database subnets (nutrition-dev-db)
Public AccessDisabled (publicly_accessible = false)
EncryptionEnabled with AWS KMS (storage_encrypted = true)
Credential ManagementAWS Secrets Manager managed password (manage_master_user_password = true)
Schema MigrationFlyway migrations V1–V11 executed by Spring Boot

Key Security Properties:

  • RDS cannot be reached from the Internet, preventing public exposure and credential attacks.
  • Security Group accepts inbound traffic on PostgreSQL port (5432) exclusively from nutrition-dev-ecs tasks.
  • Master password is generated and rotated automatically by Secrets Manager, never stored as plaintext in code or tfstate.
  • Flyway guarantees deterministic, versioned schema state.

vpc_security_group_ids = [var.security_group_id]
publicly_accessible    = false
multi_az               = var.multi_az

manage_master_user_password = true delegates database credentials to Secrets Manager directly.

  • Multi-AZ: No (Single-AZ).
  • Public access: No.
  • Security Group: nutrition-dev-rds.

5.3.3. Amazon Cognito Authentication

A. Learning Objectives

Provision a centralized user authentication system, issue JWT tokens, and enforce Role-Based Access Control (RBAC).

B. Cognito Architecture

According to system security architecture:

  • User Pool (nutrition-dev-users): Email-based user identification, automated verification email dispatch, and strong password enforcement (8+ chars, uppercase, lowercase, numbers, symbols).
  • App Client (nutrition-dev-spa): Designed for Single Page Applications (React SPA) with generate_secret = false because browser clients cannot securely hold secret keys.
  • Authentication Flows: Utilizes Secure Remote Password protocol (ALLOW_USER_SRP_AUTH) and refresh tokens (ALLOW_REFRESH_TOKEN_AUTH). Does not use Cognito Hosted UI, opting for embedded React authentication screens.
  • User Groups: Two pre-configured groups: USER (customers) and ADMIN (store administrators).
  • Backend JWT Verification: Spring Boot Resource Server verifies JWT cryptographic signatures against Cognito JWKS, extracting user identity from claim sub and authorities from claim cognito:groups.

C. Step-by-Step Implementation

1 Review Cognito Terraform Module

Inspect infra/modules/cognito/main.tf for User Pool, App Client, and recovery settings:

HCL
resource "aws_cognito_user_pool_client" "spa" {
  name            = "${var.name_prefix}-spa"
  user_pool_id    = aws_cognito_user_pool.users.id
  generate_secret = false

explicit_auth_flows = [
“ALLOW_USER_SRP_AUTH”,
“ALLOW_REFRESH_TOKEN_AUTH”,
“ALLOW_ADMIN_USER_PASSWORD_AUTH”,
]
}

2 Review USER and ADMIN User Groups

Verify user group definitions in infra/modules/cognito/main.tf:

HCL
resource "aws_cognito_user_group" "admin" {
  name         = "ADMIN"
  user_pool_id = aws_cognito_user_pool.users.id
}

resource “aws_cognito_user_group” “user” {
name         = “USER”
user_pool_id = aws_cognito_user_pool.users.id
}

Registered users belong to USER. Only users assigned to ADMIN are granted access to administrative order and catalog endpoints.

3 Deploy Cognito Module

Cognito is managed as code and provisioned during the root apply step. Do not manually create user pools in the AWS Console to avoid state drift.

4 Inspect Cognito in AWS Console

Navigate to Amazon Cognito → User pools and select nutrition-dev-users:

  • Verify User Pool ID prefix: ap-southeast-1_....
  • Under App integration → App clients: Verify client nutrition-dev-spa with No client secret.
  • Under Groups: Verify ADMIN and USER groups exist.
5 Verify API Authorization Enforcement (per docs/demo.md)

Verify backend Spring Boot RBAC enforcement against incoming API calls:

  • Unauthenticated Requests: Calling protected endpoints without an Authorization: Bearer <token> header responds with HTTP 401 Unauthorized.
  • Standard User accessing Admin API: A user in group USER attempting to access /api/admin/** triggers a claim inspection on cognito:groups and responds with HTTP 403 Forbidden.
  • Admin User: Validated successfully and granted administrative permissions.

aws ecr get-login-password –region ap-southeast-1 | docker login –username AWS –password-stdin $ECR_URL

docker build –platform linux/arm64 -t $ECR_URL:latest .


5. Push image to Amazon ECR


docker push $ECR_URL:latest

Terminal

terraform apply -var="app_running=true" -var="api_desired_count=1" -auto-approve

npm install
npm run build

cd ../infra/envs/dev
FRONTEND_BUCKET=$(terraform output -raw frontend_bucket_name)
DIST_ID=$(terraform output -raw cloudfront_distribution_id)
cd ../../../frontend


aws s3 sync dist/ s3://$FRONTEND_BUCKET/ –delete
aws cloudfront create-invalidation –distribution-id $DIST_ID –paths “/*"

5.5 – Amazon Bedrock Integration

1. Learning Objectives

  • Request model access for Amazon Nova 2 Lite in Tokyo (ap-northeast-1).
  • Configure Bedrock Guardrails to mitigate prompt injection and medical diagnostic queries.
